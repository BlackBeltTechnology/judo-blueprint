# Proposal

## Why

The catalog depends on two things that keep changing:

- **A tool syntax.** Blueprints embed `judo-cli` GraphQL queries and mutations (~1,169 lines in `model-blueprints/*/model.md`). The new CLI makes them stale.
- **An agent runtime.** The tooling is Claude Code: 4 commands, 6 agents, the docwriter skill, and 61 `$CLAUDE_PROJECT_DIR` references.

The team works in pi with the pi-dashboard kb. The catalog should therefore be:

- tool-agnostic: abstract text plus Mermaid diagrams generated by the CLI;
- shaped for `kb_search` / `kb index`;
- maintained by reusable pi skills;
- released by CI as tags that any JUDO project can pin, both as a kb source and as a pi package.

## What Changes

### 1. Entry format: descriptions + Mermaid only, no CLI anywhere in the catalog
- **BREAKING:** catalog entries contain **only abstract descriptions and Mermaid**. That means no GraphQL, no CLI commands, no `judo.sh`, and no recipes or command lists of any kind. Each entry has:
  - abstract sections: intent, structure, constraints, variations, when to use, when to avoid, related;
  - layer guidance for backend and frontend;
  - Mermaid diagrams.
- **Structure diagrams are generated by the CLI from a fragment model.** Each model-shaped entry has a **fragment**, `fragments/<id>.model`: a small ESM model built with the CLI and saved by it. It is model data (XMI), not CLI syntax, so it does not go stale when command syntax changes, and it lives outside `catalog/`.
- **How a fragment is built:** the author builds it in a scratch copy of `tests/fixtures/Sandbox.model` with the CLI's element commands (`create -t … --ns …`, `update`, `fill`; fields found with `--schema`). Neutral names are used. The CLI writes the file with `save`. The commands themselves are never stored. Fragments are never edited by hand.
- **The diagram:** `mermaid model -m fragments/<id>.model --scope bp::<id> …` writes the diagram between generated markers in the entry.
- **Best practices** with a model shape get a fragment and a generated diagram. Backend- or frontend-only practices have none.
- **Behaviour diagrams** (`stateDiagram-v2`, `sequenceDiagram`) stay hand-written, because the CLI draws only class diagrams.
- **BREAKING:** the GraphQL in `model.md` and `CONVENTIONS.md` is removed outright. It stays readable at the git tag `archive/pre-kb-restructure`, where it serves as one-time input for building the fragments.

### CLI capabilities this change uses (`judo-model-cli` `develop` @ `9f6a4bd`)
| Capability | Used for |
|---|---|
| `mermaid model --scope/--depth/--split/--kinds/--members/--md`: in-memory ESM to `classDiagram` with composition `*--`, aggregation `o--`, generalization, `..>` maps/enum/principal, two-way relations on one line, multiplicities, `<<Entity>>`/`<<Enumeration>>`/`<<Transfer>>`/`<<Actor>>` stereotypes, `<<external>>` stubs | generated entry diagrams; diagrams of a consumer's own model |
| `create -t <Type> --ns <parent>`, `update <fqn> --set/--add/--remove`, `fill`, `relocate`, `move`, `split`: one transaction each, `--dry-run`, `--schema` field discovery, `fix` lines on errors | building fragments interactively (commands never stored) |
| `validate --strict`: non-zero on any error; ESM EVL + esm2ui/UI EVL + transform dry-run | every fragment must be valid |
| `transform` (ESM to PSM/ASM/RDBMS, esm2ui) | optional check that a fragment derives cleanly |
| `save` (EMF Compare summary), `status`, `discard` | writing fragments; clean scratch sessions |
| `query esm <Type> --select --where` (read-only) | sweep: inspecting source project models |

Only the released CLI jar is used. Its command documentation (`--help`, `--schema`, the CLI repo's `judo-cli` docs) is linked, not copied.

### 2. Evidence instead of scores
- **BREAKING:** the derived `score` field and the scoring scripts are removed.
- Entries keep the inputs to the score:
  - `projects`;
  - `evidence` (`project@sha:path`, `session:<id>`);
  - `first_seen` / `last_updated`;
  - `alternatives`, as `[[wikilinks]]`.
- A fixed-threshold `status` (`single-project` / `emerging` / `established`) is added. Project preference stays in the `PROJECTS.md` weights.

### 3. kb conformance and agent-docs
- One consumable root, `catalog/`, holds `best-practices/`, `model-blueprints/` and `agent-docs/`.
- kb-parseable frontmatter: single-line values; `title`, `description`, `aliases`, `keywords`, `tags`, `status`.
- Chunk-sized headings, wikilinks, a DOX `AGENTS.md` per directory, a full reindex, and a `kb eval` golden-set gate.
- **agent-docs come first, and judo-blueprint now owns them.** The template removed `agent-docs/**` on `develop` (`5bddd8b`, 2026-11-03, `extract-agent-tooling-from-template`: "The guides are maintained in `judo-blueprint`"). There is no ongoing sync. Instead there is one **one-time** pass, before any blueprint work:
  1. **import** the last template version (`5bddd8b^`, 70 docs outside `domain/`): Handlebars rendered to static markdown, harness-neutral wording, the `feature/cciu-model-patterns` additions merged in, and `domain/` dropped (it was per-project and the template no longer generates it);
  2. **kb-ify** them: kb frontmatter, chunk-sized headings, wikilinks, a DOX `AGENTS.md` per directory, and golden queries;
  3. **verify them against judo-ng** (platform knowledge): explorer subagents compare each doc area with the judo-ng sources, i.e. the metamodels (`models/judo-meta-*`), runtime (`runtime/judo-runtime-core*`, dispatcher, DAO, security/access manager, `osgi-*`), generators/templates (`template/judo-ui-react-template`, `judo-ui-e2e-template`, `judo-psm-generator-*`, the fullstack template root) and the CLI. They also read judo-ng's own package docs (41 `agent-docs` files in `judo-runtime-core`, `SKILL.md` in metamodel packages). **Every finding they bring up is reviewed by the operator** before any doc changes;
  4. later updates to agent-docs are ordinary PRs.

  This pass is **not part of any skill**. It runs once, from the operator's session, with subagent prompts kept in this change folder.

### 4. Knowledge sources
- **Sweep:** `rackinspect` and `mlszksz-platform` are re-swept fresh at their `develop` SHAs. Inputs are model, backend, frontend, `openspec/specs` (174 and 88 specs), and project skills/agent-docs. Today, 72 entries rest on these two projects alone.
- **Session distillation:** 550 exported pi sessions (2 developers building rackinspect, ~1 GB, kept outside the repo) and the CLI audit log are run through the existing `distill-session-knowledge` engine.
  - Only patterns that recur in at least 3 sessions become candidates.
  - Each candidate is routed to exactly one target: catalog entry, CLI note upstream (for the CLI's own skill), or excluded. agent-docs findings from a sweep go to a review list, never straight into the docs.
  - A redaction check and human review gate every candidate. Candidates land in the project's contribution branch (`project/<project-id>`) and reach `develop` through the merge criteria; there is no separate consent record.
  - `MEMORY.md` is optional reading for the reviewer. It is not mined by a separate script.

### 5. Reusable pi skills (replace all Claude tooling)
The repo is a **pi package**. `package.json` `pi.skills` exports the reusable skills, so any project can `pi install git:github.com/BlackBeltTechnology/judo-blueprint@v<version>`. There are no slash commands, prompt templates, agents or flows.

| Skill | Exported | For | Scripts |
|---|---|---|---|
| `judo-blueprint` | yes | any JUDO project: find and apply catalog entries with `kb_search`, pin the catalog version | `pin-source` |
| `judo-model-mermaid` | yes | any JUDO project: render Mermaid for a fragment or for a scope of the project's own model; check that a fragment is valid and matches its diagram | `render`, `check` |
| `judo-blueprint-author` | yes | write or update one entry (description, fragment built with the CLI, generated Mermaid), also from consumer projects as a PR back here | `scaffold-entry` (entry + scratch Sandbox), `entry-lint` |
| `judo-session-distill` | yes | distill any JUDO project's pi sessions into reviewed candidates | `distill-run`, `distill-route`, `redact-check` |
| `judo-catalog-maintain` | no (`.pi/skills/`) | this repo only: sweep projects, rewrite batches, gates, release (blueprints and best practices only; no agent-docs/platform-knowledge update) | `sweep-plan`, `clone-project`, `record-sweep`, `projects.py`, `next-batch`, `sweep-prepare`, `model-overview`, `custom-overview`, `sweep-merge`, `sweep-publish`, `sweep-overlap`, `check-all`, `version.sh`, `release-notes` |

- **Judgement work** (analysis, authoring, routing ambiguous candidates) is done by the model in the session, guided by each skill's `references/`.
- **Deterministic work** is done by scripts, and CI calls the same scripts.
- **Composition:** skills compose through documented script calls. For example, `judo-blueprint-author` calls `judo-model-mermaid/scripts/render`.
- **The jar:** `judo-cli.jar` is untracked; it is ~99 MB and committed today despite `.gitignore`. It is downloaded by the pom profile into `target/` at the pinned CLI version.

### 6. Release and Sandbox gate
- **Versions** follow the JUDO NG scheme from `judo-maven-plugin`:
  - branch builds get `v<base>.<yyyyMMdd_HHmmss>_<shortSha>_<branch>` as prereleases;
  - `master` gets `v<base>` as a full release.
- **Tags are immutable** and are created only when every gate passes.
- **Consumers pin one tag** for both the kb `git` source (`pin`, `subdir: catalog`) and `pi install …@<tag>`.
- **Sandbox gate:** after the full sweep, after distillation, and on every PR and release, every fragment must:
  - pass `validate --strict`;
  - keep its generated Mermaid block equal to a fresh `mermaid model` render.

  A model-shaped entry without a passing fragment blocks the release.

### 6b. Sweep with subagents (no flows)
- The operator's session runs the sweep step by step, following `judo-catalog-maintain/references/sweep.md`:
  1. scripts create the worktrees: a detached source worktree, plus a blueprint branch `sweep/<project>-<sha>`;
  2. scripts build the model and custom-code overviews;
  3. 4 explorer subagents (model, backend, frontend, schema) run in parallel, each searching the catalog with the kb CLI;
  4. a script merges the candidates; a cross-validate subagent proposes decisions, and **the operator approves them**;
  5. author subagents write the entries in the blueprint worktree;
  6. gates run, with up to 3 fix rounds;
  7. the PR is opened **after the operator confirms**.
- Subagent definitions: `.pi/agents/judo-sweep-*.md`. All state is JSON files in the gitignored work folder, so any lane can be re-run on its own.

**Candidates in consumer projects** (each project decides; not done in this change): after installing the package, rackinspect's own skills overlap with it:
- `judo-blueprint` (local clone) is replaced by the packaged `judo-blueprint`;
- `judo-model-cli` and `judo-model-cli-mutations` (old command and GraphQL docs) are superseded by the CLI repo's own `judo-cli` skill, `--help`/`--schema`, and the template's `model/judo-cli.md`;
- `judo-{backend,frontend,model,deployment,e2e-testing,integration-testing}-docs` duplicate the catalog `agent-docs`, which are reachable through kb;
- `judo-agent-docs-gap` is replaced by `judo-blueprint-author`.

In mlszksz, `.claude/skills/{judo-cli,cli-tester}` are stale copies of skills that now live in the CLI repo.

## Capabilities

### New Capabilities
- `blueprint-format`: entries hold only descriptions and Mermaid: abstract sections, the generated-diagram rule, layer files, a ban on any CLI, GraphQL or command content, and evidence frontmatter without a score.
- `catalog-kb-indexing`: kb index conformance: catalog root, frontmatter, headings and chunks, wikilinks, DOX `AGENTS.md`, kb config, reindex, and the `kb eval` gate.
- `catalog-release-versioning`: JUDO NG versions, immutable gated tags, releases, and consumer pinning for both kb and the pi package.
- `agent-docs-catalog`: agent-docs owned by this repo: one-time import from the last template version, kb conformance, and a review-gated verification against judo-ng; static lint only, no template sync.
- `blueprint-sandbox-validation`: each fragment model passes the pinned CLI's `validate --strict`, and its generated Mermaid matches a fresh `mermaid model` render; release gate.
- `session-knowledge-distillation`: exported sessions turned into reviewed candidates: corpus contract, routing, evidence, redaction, review, and incremental re-runs.
- `catalog-contribution-branches`: per-project contribution branches (`project/<project-id>`) that the project's kb reads, a contribution guide that aligns contributors with the catalog's methods, published merge criteria, and a `branch-review` tool; replaces contributor consent.
- `catalog-collection-agents`: the reusable pi skills package (exported versus internal skills, scripts usable standalone and by CI, composition, and the sweep).

## Impact

- **Content:** 105 blueprints and ~222 best practices are rewritten, each with a CLI-built fragment where it has a model shape. agent-docs are imported once, kb-ified and verified against judo-ng first.
- **New:**
  - `package.json` (pi package), `skills/` (4 exported), `.pi/skills/judo-catalog-maintain/`;
  - `fragments/` (ESM fragment models, outside the catalog);
  - release and lint workflows, pom `revision`;
  - kb config and the golden set;
  - `skills/judo-blueprint/references/contribute.md`, `skills/judo-catalog-maintain/references/merge-criteria.md`, `scripts/branch-review`.
- **Prerequisites:**
  - the new CLI is merged (done: `develop` @ `9f6a4bd`, 2026-11-03, with `mermaid model` and the authoring commands). Its build version is pinned when work starts;
  - `feature/cciu-model-patterns` and `feature/rackinspect-…` are merged to `develop`;
- **Cross-repo:** the template's stage 2 unblocks once this lands. Consumers switch to the tag pin.
- **Open:** whether judo-ng package docs (`judo-runtime-core` agent-docs, `SKILL.md` in `judo-meta-*`, `judo-model-cli`, `osgi-filestore`) are referenced as extra kb sources or distilled. This is a follow-up.
- **Out of scope:**
  - sweeping other projects;
  - kb or distiller engine changes;
  - removing skills inside consumer projects.
