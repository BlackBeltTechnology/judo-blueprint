## Overview
- react-i18next; translation files in `public/i18n/`, multiple languages.

## Directory Structure
- Flat layout, NOT subdirectories (`en-US/translation.json` is wrong).
- Naming `{type}_{locale}.json`: `application_*.json` (generated from model: entities, enumerations, menu, services); `system_*.json` (JUDO platform UI: buttons, modals, table controls); `*_default.json` = fallback.
- Generator writes `application_default.json` and `application_<locale>.json` only for the model's default language. Other locale files (e.g. `application_hu-HU.json` in a one-language model) are hand-maintained.
- Derived strings (model expression members) are fixed text, not translated. Format display text in the frontend.

## Translation File Format
- Flat dot-notation keys, not nested objects.
- Key patterns: `entities.[Entity].[Component].[field]`; `enumerations.[EnumType].[VALUE]`; `enumerations.[EnumType]._null`; `menuTree.[MenuLabel]`; `menuTree.other` (phone bottom bar overflow, not generated; `BottomMenu` falls back to `Other`); `services.[service].[Entity].[Component].[field]`; `faults.<app>.[path].[Fault].[field]` (fault messages; see Frontend Error Handling); `extra.localization.operation.[operationName]`.
- Sections: structure, key naming conventions, example `application_default.json`, `application_hu-HU.json`, `system_default.json`, `system_hu-HU.json`.

## Using Translations in Code
- `const { t } = useTranslation()`; `t('key')`.
- Parameters: `t('validation.minLength', { min })`.
- Pluralisation: keys `count_one` / `count_other` with `{{count}}`.
- Flat keys: pass full key string to `t`.
- Current language: `i18n.language` from `useTranslation()`.

## Language Switching
- Get current language, `i18n.changeLanguage(...)`, language dropdown, register in AppBar.

## Adding New Languages
- Steps: copy existing `application_*.json` and `system_*.json` files; translate application content; translate system strings; update the language selector.
- `src/l10n/l10n-context.tsx` exports `locales` (date-fns locales) containing `en-US` plus the model's default language only. `setLocale` accepts only those keys; other languages need a cast, and date pickers keep `en-US` formatting unless a date-fns locale is added to the map.

## Custom Translation Provider
- Default: translations load from `public/i18n/`. Usually no custom provider needed.
- Advanced: custom `L10NTranslationProvider` (from `~/l10n/l10n-context`, with `L10NTranslations`) to load dynamic translations from backend. Prefer model-maintained files.

## Date and Time Formatting
- Timestamps display in browser time zone (not model or user profile zone). Store UTC.
- date-fns with i18n locales (`enUS`, `hu` from `date-fns/locale`); number formatting via `i18n.language`; currency formatting.

## Best Practices
- Don't edit generated `application_*.json` (`application_default.json` and `application_<default-language>.json`); changes lost. Hand-edited generated file is overwritten or fails checksum unless listed in `.generator-ignore`; once ignored it stops following model changes. See generator-ignore i18n layout best practice.
- Use flat dot-notation keys; follow JUDO key conventions.
- Keep language files in sync (diff key lists with `jq`).
- Use parameters for dynamic content.
- Test all languages (`i18n.changeLanguage`).
- Always keep `application_default.json` and `system_default.json` as fallbacks.
- Translate enumerations including `_null`.

## Troubleshooting
- "Translation key not found": check key path, verify key exists in file.
- "Language not changing": clear i18n cache; check language code.
- "Translations not loading": verify file location under `public/i18n/`, JSON syntax, structure.
