- Optimistic locking is **on by default** in the RDBMS runtime (`rdbmsDaoOptimisticLockEnabled = true`). Inserts set the version to 1; each write increments it.
- The check happens in `UpdatePayloadDaoProcessor` and **only when the update payload contains `__version`**: it must equal the stored version, otherwise `IllegalArgumentException("Outdated instance to update")`. ## AuthenticationInterceptor Interface
- Methods: `getName()`, `isSuitableForOperation(EOperation, claim, realm, client, attributes)`, `authenticate(operationFQName, exchange, claim, realm, client, attributes)`, `success(EOperation, SignedIdentifier, exchange, claim, realm, client, attributes)`.

## Practice

### Four parts

1. An interface in business terms (connection check, list items, read cost to date). It uses plain DTOs, not provider types and not generated entity types.
2. One adapter class per provider. It is the only place with provider SDK calls, query languages, unit conversions (for example micro-currency) and paging or streaming of big results.
3. A provider service, an OSGi component, that reads the entity's platform attribute (an enumeration), loads the credentials and returns a new adapter instance.
4. DTOs for the data crossing the boundary, mapped to entities by the calling service.

The interface, adapters and provider service are application code. The platform only supplies the OSGi wiring (`@Reference`, `@Component`) used to reach the provider service from a custom operation (see [Example 3: External Service Integration](../../agent-docs/backend/custom-operations.md#example-3-external-service-integration) and [The Custom Service Layer](../../agent-docs/backend/architectural-patterns.md#2-the-custom-service-layer)).

### Resolution order (`DefaultActorResolver`)

`ActorResolver` is the SPI that maps a `JudoPrincipal` or token claims to the persisted actor payload: `authenticateActor(Map exchange)`, `authenticateByPrincipal(JudoPrincipal)` (returns `Optional<Payload>`) and `getActorByClaims(EClass actorType, Map claims)`. `JudoDefaultModule` wires `DefaultActorResolver`; bind your own implementation to add custom matching, just-in-time provisioning or rejection.

`getActorByClaims` chooses the lookup attribute in this order:

1. the attribute with `claim = USERNAME`, if its claim is present in the token;
2. the attribute with `claim = EMAIL`, if present;
3. the first identifier attribute (sorted by name) whose name is in the claims; otherwise `IllegalStateException`.

It then runs `dao.search` on the actor type, so **the actor row is read from the database on every request that carries a principal**. Zero matches give `AccessDeniedException` `AUTHENTICATED_ENTITY_NOT_FOUND`; several matches give `SecurityException` ("Multiple actors found in database by token"). When the principal resolution is slow, profile this read (index the claim column) rather than the application's `#_principal` interceptor. `authenticateByPrincipal` runs only when the exchange has no actor yet and `checkMappedActors` is `true` (default `false`). Claims whose matching attribute is `transient` are copied onto the returned actor payload.

- Every instance the REST layer returns carries `__identifier` and a `__signedIdentifier`. Bound operations and instance updates take the signed identifier (request header `X-Judo-SignedIdentifier`), not the plain id.
- The signature covers the id, the entity type, the entity **`__version`** and an **immutable** flag (`DefaultIdentifierSigner`). Because the version is part of the token, **the signed identifier changes after every update** of the entity. A signed identifier you stored earlier can therefore differ from the current one.
- Signing uses a key: a configured HMAC `secret` or, if none is configured, a key generated at start. With a generated key all previously issued signed identifiers become invalid after a restart, and nodes of a cluster cannot validate each other's tokens. Configure a stable secret in production.
- Server or client code **cannot mint** a signed identifier; the runtime signs identifiers only while serving a response. Code that needs the signed id of an instance must obtain it from a response of the API.
- `immutable`: instances produced from an `immutable` copy carry the flag inside the signed identifier. The dispatcher refuses exposed operations on such instances with `AccessDeniedException` (`BOUND_OPERATION_INSTANCE_IS_IMMUTABLE`).

**What gets generated** in `migration/<previous>_to_<latest>/` (dots and dashes of the versions become underscores):
- an aggregated `00_<app>_incremental_<dialect>.changeset.xml` plus eight phase changesets: `check`, `backup`, `beforeIncremental`, `updateDataBeforeIncremental`, `incremental`, `updateDataAfterIncremental`, `aferIncremental` (sic, script `07_aferIncremental`) and `dropBackup`;
- the model `<app>-rdbms_<version>_<dialect>.model`;
- marker files `latest.version` and `previous.version` in the output directory, which drive base/update version resolution for the next run.

Only changesets that contain developer knowledge matter in practice: the data-migration changesets (`updateDataBeforeIncremental`, `updateDataAfterIncremental`) are empty unless you write them.

Business rules depend on "now": the next working day, a time window, an expiry. If each class reads `LocalDate.now()` itself, tests and demos cannot move time and different classes can disagree on the time zone. Keep one clock in one place, read it everywhere, and allow a start-up override so a test or demo can run at a chosen date.

## Practice

### Platform base

- `Timestamp!now()` in model expressions follows the platform parameter `defaultZoneId`, while `LocalDateTime.now()` in custom Java follows the JVM time zone ([Time and Time Zones](../../agent-docs/backend/platform-behavior-reference.md#time-and-time-zones)). A single clock for custom Java removes that second source of divergence in Java code, but not in model expressions.
- Custom operations are OSGi components that reach services with `@Reference` ([custom operations](../../agent-docs/backend/custom-operations.md#osgi-component-registration-pattern)). Interceptors are also components ([the interceptor contract](../../agent-docs/backend/interceptors.md#the-interceptor-contract)).

[6313] TOOLRESULT: ## Backend guidance

Plain lookups need no custom backend code. The generated DAO covers read, and the project's access and transfer objects decide who may write. Backend code appears only for seeding, name checks and bulk management.

### Seeding at startup

Initial rows are created once by a static initializer operation with the generated DAO. In the source projects the initializer seeds cities (about 250, with postal code links), capabilities and similar lists. The initializer is project code, not a platform hook. See [[init-data-seeding]].

### Management through a shared service

One project service (an example name, such as `MasterDataService`) holds create, update and toggle-active for the lookups. The custom operations are thin wrappers that delegate to it. Its main job is the rule the model does not express: name uniqueness checked before create and update. The service and operation classes are project code, not platform API. Interceptors do not run for custom operations, so the rule lives in the service. See [[capability-lookup-entity]] for the same shape with a flag.

An operation that receives a multi-select resolves the chosen entries by identifier through the generated DAO. The DAO's `getById` fetches one entry. In the source project the selected names are then joined into one denormalized string for display, which is project practice, see [[aggregated-stored-field]]. ## Practice
- `identifier` is a flag on a `DataMember`. It is available only when the container is an entity type and the member is `STORED` ([structure.md](../../agent-docs/model/esm_metamodel/structure.md), *DataMember Attribute Rules*). The docs call it the natural key field.
- Put the flag on two or more required String attributes, for example `code` and `name`.
- The `code` is usually produced by a default expression (see [[sequence-based-identifier]] and [[default-value-patterns]]); the name is entered by the user.
- Transfer objects that need to show or look up the entity expose both attributes as mapped members.
## Rationale
Entities often have a stable machine code and a label people recognise. Flagging both as identifiers documents both as natural keys in the model.
The agent-docs only say that `identifier` marks a natural key; they do not state how the flag on several attributes is enforced at runtime. Treat uniqueness of the combination and of each part as something to verify in the generated schema or to enforce in project code, and say so in the model's documentation.
## Example
A `Country` entity has two required String attributes flagged as identifiers, `code` and `name`, plus an ordinary `population` attribute. Seen in two projects, where up to four representations of one record (code, name, two ISO alphas) are flagged.
